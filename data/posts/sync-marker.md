我们已经习惯了使用分布式文件系统对数据进行分片存储，使用分布式计算引擎对这些数据进行并行处理，但是，数据文件通常是由记录（Record）组成的，例如，文本文件由「行」组成，SequenceFile 由「KV 键值对」组成，因此，当一个文件被拆分并由不同计算节点负责处理时，需要保证记录的完整性，避免同一个记录被拆分到不同计算节点，这需要文件格式和计算引擎两方的配合。



# Sync Marker

想要保证记录的完整性，就要有一种机制来确定记录的边界——从哪个字节开始，到哪个字节结束。我们可以在两条记录之间插入一个特定的标识。对于文本文件（未压缩），可以直接使用以换行符作为标识；对于 SequenceFile、Avro 这些存储格式，则依赖 Sync Marker。

以 SequenceFile 为例，若干条 KV 记录组成一个 64K 左右的 SequenceFile-Block（不是 HDFS Block），SequenceFile-Block 内的记录都是完整的，不存在一条记录被拆分到不同的 SequenceFile-Block 的情况。SequenceFile 在创建文件时随机生成 16 字节的标识，并存入文件头，这个标识就是 Sync Marker。随后，在文件内容中，SequenceFile-Block 之间，都会被插入 Sync Marker，与此相关的源码有兴趣的小伙伴可以阅读 `org.apache.hadoop.io.SequenceFile`。

当一个 SequenceFile 文件被存入 HDFS 时，会进行分片，文件被分为若干个 HDFS-Block，一般大小为 128M，这是一个暴力过程，并不保证记录的完整性，很可能一条记录被拆分到不同的 HDFS-Block 中。这也符合 HDFS 的定位——分布式存储系统，让它来负责记录的完整性是不合适的，因为这需要深入文件内部。

当计算引擎（如 MapReduce）在处理这个文件时，会首先对它进行逻辑上的拆分，形成若干个 Split（如无特殊的代码实现，一个 Split 就是一个 HDFS-Block），这个 Splitting 过程也不处理记录的边界问题。直到真正读取 Split 数据时才开始处理这个问题，核心的处理逻辑是：在处理第 N 个 Split 时，总是额外读取到第 N+1 个 Split 的第一个 Sync Marker；而在读取第 N+1 个 Split 时，总是从该 Split 的第一个 Sync Marker 之后开始读取。这部分逻辑，后文会给出相关的 Hadoop 源码解读。

# 压缩的影响

压缩是否会影响记录边界的确定，进而导致无法对文件进行并行处理？

如果在文件级别进行压缩，那么它是否可并行处理取决于压缩算法。举一个实测的例子：同一个 TextFile，GZip 压缩（压缩后约 700M），MapReduce 在执行时，Split 数为 1，可见是无法并行处理的；而 BZip2 压缩（压缩后约 470M），MapReduce 在执行时，Split 数为 4，可见是可以并行处理的。GZip 压缩算法由于算法自身特性的原因，解压某一部分数据时，需要来自前一部分数据的一些信息，即整个压缩过程前后存在依赖，所以只能从头到尾解压，不能并行处理。

TextFile 只能进行文件级别的压缩，但是 SequenceFile、Avro 等文件格式（也称为 Container File Format），支持块级别（甚至记录级别）压缩，这种情况下，Sync Marker 仍然存在，因此始终是可以并行处理的，无论使用哪一种压缩算法。



# 源码

真正对记录边界的处理是在对应的*RecordReader 类中，通过源码可以比较清晰地了解（以 Hadoop MapReduce 2.7.1 版本为例），以下的类都位于 org.apache.hadoop.mapreduce.lib.input 包中。

```java
public abstract class FileInputFormat<K, V> extends InputFormat<K, V> {

  // 标识此文件是否可拆分，基类中默认返回true，可在子类中根据具体情况重写。
  // 注意，如果返回false，则MR等引擎无法对其进行并行处理，意味着，以MR为例，只会有一个Mapper实例来处理整个文件。
  // 一个文件是否可拆分，主要取决于外部程序是否能探知记录的边界，如无法知道，则无法拆分。
  protected boolean isSplitable(JobContext context, Path filename) {
    return true;
  }

  // 对输入文件进行Split，核心逻辑比较简单，大体就是从文件起始位置开始，根据Split Size，依次设置各个Split的起始和结束Offset。
  // 同时附上各Split所在Block的物理位置（哪些节点上，包括哪些节点当前有相关Block的缓存）。
  // 此处，没有看到对记录边界的处理。
  public List<InputSplit> getSplits(JobContext job) throws IOException {
    StopWatch sw = new StopWatch().start();
    long minSize = Math.max(getFormatMinSplitSize(), getMinSplitSize(job));
    long maxSize = getMaxSplitSize(job);

    // generate splits
    List<InputSplit> splits = new ArrayList<InputSplit>();
    List<FileStatus> files = listStatus(job);
    for (FileStatus file: files) {
      Path path = file.getPath();
      long length = file.getLen();
      if (length != 0) {
        BlockLocation[] blkLocations;
        if (file instanceof LocatedFileStatus) {
          blkLocations = ((LocatedFileStatus) file).getBlockLocations();
        } else {
          FileSystem fs = path.getFileSystem(job.getConfiguration());
          blkLocations = fs.getFileBlockLocations(file, 0, length);
        }
        if (isSplitable(job, path)) {
          long blockSize = file.getBlockSize();
          long splitSize = computeSplitSize(blockSize, minSize, maxSize);

          long bytesRemaining = length;
          while (((double) bytesRemaining)/splitSize > SPLIT_SLOP) {
            int blkIndex = getBlockIndex(blkLocations, length-bytesRemaining);
            splits.add(makeSplit(path, length-bytesRemaining, splitSize,
                        blkLocations[blkIndex].getHosts(),
                        blkLocations[blkIndex].getCachedHosts()));
            bytesRemaining -= splitSize;
          }

          if (bytesRemaining != 0) {
            int blkIndex = getBlockIndex(blkLocations, length-bytesRemaining);
            splits.add(makeSplit(path, length-bytesRemaining, bytesRemaining,
                       blkLocations[blkIndex].getHosts(),
                       blkLocations[blkIndex].getCachedHosts()));
          }
        } else { // not splitable
          splits.add(makeSplit(path, 0, length, blkLocations[0].getHosts(),
                      blkLocations[0].getCachedHosts()));
        }
      } else { 
        //Create empty hosts array for zero length files
        splits.add(makeSplit(path, 0, length, new String[0]));
      }
    }
    // Save the number of input files for metrics/loadgen
    job.getConfiguration().setLong(NUM_INPUT_FILES, files.size());
    sw.stop();
    if (LOG.isDebugEnabled()) {
      LOG.debug("Total # of splits generated by getSplits: " + splits.size()
          + ", TimeTaken: " + sw.now(TimeUnit.MILLISECONDS));
    }
    return splits;
  }

  // 计算Split的大小，与一些参数设置相关，不过，通常Split Size就是Block Size。
  protected long computeSplitSize(long blockSize, long minSize,
                                  long maxSize) {
    return Math.max(minSize, Math.min(maxSize, blockSize));
  }
}
```

```java
      new CompressionCodecFactory(context.getConfiguration()).getCodec(file);
    if (null == codec) {
      return true;
    }
```

```java
public class LineRecordReader extends RecordReader<LongWritable, Text> {
  private static final Log LOG = LogFactory.getLog(LineRecordReader.class);
  public static final String MAX_LINE_LENGTH = 
    "mapreduce.input.linerecordreader.line.maxlength";

  private long start;
  private long pos;
  private long end;
  private SplitLineReader in;
  private FSDataInputStream fileIn;
  private Seekable filePosition;
  private int maxLineLength;
  private LongWritable key;
  private Text value;
  private boolean isCompressedInput;
  private Decompressor decompressor;
  private byte[] recordDelimiterBytes;

  public void initialize(InputSplit genericSplit,
                         TaskAttemptContext context) throws IOException {
    FileSplit split = (FileSplit) genericSplit;
    Configuration job = context.getConfiguration();
    this.maxLineLength = job.getInt(MAX_LINE_LENGTH, Integer.MAX_VALUE);
    start = split.getStart();
    // 此处注意，是start + split.getLength()，不是start + split.getLength() - 1，
    // 所以，‘end’作为索引的话，实际上是超出当前Split的边界的，是当前Split边界后的第一个字符。
    end = start + split.getLength();
    final Path file = split.getPath();

    // open the file and seek to the start of the split
    final FileSystem fs = file.getFileSystem(job);
    fileIn = fs.open(file);
    
    CompressionCodec codec = new CompressionCodecFactory(job).getCodec(file);
    if (null!=codec) {
      isCompressedInput = true;	
      decompressor = CodecPool.getDecompressor(codec);
      // 此处压缩相关的暂时忽略，只看下方非压缩部分
      if (codec instanceof SplittableCompressionCodec) {
        ...
      } else {
        in = new SplitLineReader(codec.createInputStream(fileIn,
            decompressor), job, this.recordDelimiterBytes);
        filePosition = fileIn;
      }
    } else {
      fileIn.seek(start);
      in = new SplitLineReader(fileIn, job, this.recordDelimiterBytes);
      filePosition = fileIn;
    }
    // 重点：
    // 如非文件的第一个Split，则总是跳过本split的第一条记录（第一行），因为对于每一个Split（除了文件的最后一个Split），
    // 我们总是向后多读取一条记录（一行）。通过额外多读一行的方式，很方便的解决了记录完整性的问题。
    // （以下为原注释）
    // If this is not the first split, we always throw away first record
    // because we always (except the last split) read one extra line in
    // next() method.
    if (start != 0) {
      // 参数1：用于存储所读入的内容
      // 参数2：存入参数1的最长长度，此处0表示不存入任何内容，因为我们需要跳过第一行。
      // 参数3：最长的读取长度，maxBytesToConsume见下方，可以认为就是Integer.MAX_VALUE
      // 返回值：读取到的行的长度，包含\n在内
      // 此行代码所起到的效果就是，将读取位置移到了本split的第一个\n之后的字符处。
      start += in.readLine(new Text(), 0, maxBytesToConsume(start));
    }
    this.pos = start;
  }
  

  // 此处可认为是返回Integer.MAX_VALUE
  private int maxBytesToConsume(long pos) {
    return isCompressedInput
      ? Integer.MAX_VALUE
      : (int) Math.max(Math.min(Integer.MAX_VALUE, end - pos), maxLineLength); // maxLineLength的默认值是Integer.MAX_VALUE
  }

  // 此处不考虑压缩情况，则实际上返回的就是pos
  private long getFilePosition() throws IOException {
    long retVal;
    if (isCompressedInput && null != filePosition) {
      retVal = filePosition.getPos();
    } else {
      retVal = pos;
    }
    return retVal;
  }

  // 此方法是RecordReader的重点方法，外部将循环调用该方法以读取数据
  public boolean nextKeyValue() throws IOException {
    if (key == null) {
      key = new LongWritable();
    }
    key.set(pos); // 此处可以看到，MR处理文本文件时的那个key，实际上是该行的起始位置，而不是行号。
    if (value == null) {
      value = new Text();
    }
    int newSize = 0;
    // “向后多读取一行”的逻辑。这里的关键点是“end”，前面说过，“end”的作为索引的话是当前split边界后的第一个字符。
    // 举个简单的例子，假设每一行（含\n）长度都为10，
    // 1) 假设split size为20，则split[0].end=20，读取第一行后，pos=10，读取第二行后，pos=20，
    //    pos<=split[0].end，于是向后再读取一条。
    // 2) 假设split size为15，则split[0].end=15，读取第一行后，pos=10，
    //    pos<=split[0].end，于是继续读取（到下一个\n（含）），实际上是把位于split[1]的“后半行”读取进来，保证了记录的完整性。
    // Case 1中，实际上可以不用向后多读，记录本身就是完整的，只有case 2才需要，但为了逻辑统一，所以都走了以下代码，省去了额外的判断。
    //
    // 注：in.needAdditionalRecordAfterSplit()与此逻辑无关，其值为false，不知道目的是什么，先忽略
    // （以下为原注释）
    // We always read one extra line, which lies outside the upper
    // split limit i.e. (end - 1)
    while (getFilePosition() <= end || in.needAdditionalRecordAfterSplit()) {
      if (pos == 0) {
        newSize = skipUtfByteOrderMark(); // 对文本文件的文件头就行特殊处理，可先忽略
      } else {
        newSize = in.readLine(value, maxLineLength, maxBytesToConsume(pos));
        pos += newSize;
      }

      // maxLineLength的默认值是Integer.MAX_VALUE，故绝大多数情况这里直接break跳出
      if ((newSize == 0) || (newSize < maxLineLength)) {
        break;
      }

      // 如未break跳出，说明行超长（可能是maxLineLength自定义值太小）
      // line too long. try again
      LOG.info("Skipped line of size " + newSize + " at pos " + 
               (pos - newSize));
    }
    if (newSize == 0) {
      key = null;
      value = null;
      return false; // 此split读取结束。
    } else {
      return true;
    }
  }
}
```

```java
public class SequenceFileRecordReader<K, V> extends RecordReader<K, V> {
  private SequenceFile.Reader in;
  private long start;
  private long end;
  private boolean more = true;
  private K key = null;
  private V value = null;
  protected Configuration conf;

  @Override
  public void initialize(InputSplit split, 
                         TaskAttemptContext context
                         ) throws IOException, InterruptedException {
    FileSplit fileSplit = (FileSplit) split;
    conf = context.getConfiguration();    
    Path path = fileSplit.getPath();
    FileSystem fs = path.getFileSystem(conf);
    this.in = new SequenceFile.Reader(fs, path, conf);
    this.end = fileSplit.getStart() + fileSplit.getLength();

    if (fileSplit.getStart() > in.getPosition()) {
      // 该方法会寻找下一个Sync Marker，并将读取位置移至该Sync Marker后。
      // Sync Marker是一个标识，Sequence File每隔若干个记录，会插入一个Sync Marker，
      // 注意是每隔若干个，不是每一个记录后插入。
      // 其他一些存储格式也使用类似的机制，主要是为了使用方能方便确认记录完整性。
      in.sync(fileSplit.getStart());                  // sync to start
    }

    this.start = in.getPosition();
    more = start < end;
  }

  @Override
  @SuppressWarnings("unchecked")
  public boolean nextKeyValue() throws IOException, InterruptedException {
    if (!more) {
      return false;
    }
    long pos = in.getPosition();
    key = (K) in.next(key);
    // 此处原理上和LineRecordReader差不多，就是说，即便已经读取到split的边界了，
    // 如果此次读取没有遇到Sync Marker，则继续向后一个split读取，直到遇到一个Sync Marker。
    // 由于Sync Marker标志着一组记录的结束位置，所以不会截断记录，保证了记录的完整性。
    //
    // 可能会有疑问：由于Sequence File是每隔若干个记录才插入一个Sync Marker，那么这若干个记录之间是怎么区分开的呢？
    // 由于Sequence File的每个记录形如：(Key-length 4B|Value-length 4B|Key-content|Value-content)，
    // 4个字节描述该记录中Key长度，4个字节描述记录中Value的长度，紧接着分别是Key和Value的具体值，
    // 所以，通过长度计算，很容易确定一条记录的边界。
    if (key == null || (pos >= end && in.syncSeen())) {
      more = false; // 此split读取结束。
      key = null;
      value = null;
    } else {
      value = (V) in.getCurrentValue(value);
    }
    return more;
  }  
}
```

# 除了 Sync Marker，还有其他方案吗？

ORC、Parquet 这些格式，采用另外一种方案。它们在文件尾部（ORC 中称为 File Footer，Parquet 中称为 File Metadata）存储的元数据中，包含了所有 Block(ORC 中称为 Stripe，Parquet 中称为 Column Chunk)的起止位置，利用这些信息，当然很容易确定记录的边界，缺点是需要不时更新文件尾部的元数据。
